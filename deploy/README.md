# SENTINEL HIVE — dev/test deployment (issue #36)

Reproducible local deployment of the trusted management plane + lab bridge.
**Nothing here contains secrets** — credentials are generated locally into
gitignored paths (`deploy/secrets/`, `deploy/env/*.env`,
`deploy/mosquitto/passwordfile`).

## Topology

```
 untrusted lab net                trusted management plane (this deploy/)
 ┌──────────────────┐   MQTT    ┌──────────────────────────────────────┐
 │ pucks/rover/AP/  │ ────────► │ mosquitto (per-device ACLs)          │
 │ Kismet/SDR       │  QoS1     │        │                             │
 └──────────────────┘           │        ▼                             │
                                │ services/gateway (host or container) │
                                │   ingest -> SpacetimeDB reducers     │
                                │   missions <- pendingMissions view   │
                                │   outbox   <- executorOutbox view    │
                                │        │                             │
                                │        ▼                             │
                                │ spacetimedb :3000 (authoritative DB  │
                                │   + role-scoped realtime views)      │
                                │        │                             │
                                │        ▼                             │
                                │ lab-executor :8082 (action webhook)  │
                                └──────────────────────────────────────┘
```

The dashboard/command-center clients connect to SpacetimeDB directly and
subscribe to the role-scoped views — the same path the smoke tests prove.

| Gateway deps | `services/gateway/package-lock.json` | committed lockfile |

The CLI version matters: `install.spacetimedb.com` tracks **latest**, which
can drift ahead of the pinned server/SDK. Install the matching release
directly instead (assets: `spacetime-<arch>-<os>.tar.gz`):

```sh
# macOS arm64 example — use spacetime-x86_64-apple-darwin.tar.gz on Intel,
# spacetime-aarch64-unknown-linux-gnu.tar.gz on Linux arm64, etc.
curl -fsSL -o /tmp/spacetime.tgz \
  https://github.com/clockworklabs/SpacetimeDB/releases/download/v2.14.1/spacetime-aarch64-apple-darwin.tar.gz
tar xzf /tmp/spacetime.tgz -C ~/.local/bin
ln -sf ~/.local/bin/spacetimedb-cli ~/.local/bin/spacetime
spacetime --version   # expect 2.14.1
```

## Fresh-engineer bootstrap

```sh
git clone <repo> && cd hackutd26
# prereqs: docker, node>=22.6, spacetime CLI 2.14.x (see above)
deploy/scripts/bootstrap.sh
```

`bootstrap.sh` is idempotent and performs:

0. Secrets — copies `env/mqtt.env.example` → `env/mqtt.env` if missing and
   fills any empty `*_PASSWORD` with random dev passwords; regenerates
   `mosquitto/passwordfile` (gitignored bcrypt hashes).
1. `docker compose up -d` — mosquitto, spacetimedb, lab-executor (with
   healthchecks; `docker inspect -f '{{.State.Health.Status}}' sh-<svc>`).
2. `spacetime publish sentinel-hive --delete-data=always` — fresh module.
3. `deploy/seeds` — creates **independently authenticated demo identities**
   (admin, commander, responder, observer, agent, gateway, executor, plus
   one identity per lab device), registers zones/devices/assets, enrolls
   device principals, and writes `deploy/secrets/identities.json`.
4. `services/gateway` `npm install` + binding generation, then auto-fills
   the still-empty `SPACETIMEDB_TOKEN`, `EXECUTOR_SPACETIMEDB_TOKEN` and
   `MQTT_PASSWORD` in `env/gateway.env` from those secrets (values already
   set are never overwritten).
5. Prints container health + next steps.

Then start the gateway (host process — see Topology):

```sh
cd services/gateway
set -a; . ../../deploy/env/gateway.env; set +a
npm start
curl localhost:8081/healthz
```

> **macOS note:** Docker Desktop needs Files-and-Folders access to the
> repo path. `~/Documents`, `~/Desktop` and `~/Downloads` are
> TCC-protected — if `docker compose up` fails with
> `operation not permitted` on a bind-mount source, grant Docker access in
> System Settings → Privacy & Security, or run the deploy from an
> unprotected path (e.g. `cp -R deploy ~/sh-deploy` and compose from
> there; the `spacetime-data` named volume is shared either way).

## Secret injection

- **SpacetimeDB identity tokens** — generated by `deploy/seeds/seed.ts`
  (each demo role = distinct identity+token) into
  `deploy/secrets/identities.json`; consumed via `SPACETIMEDB_TOKEN` /
  `EXECUTOR_SPACETIMEDB_TOKEN` env vars. Nothing is committed.
- **MQTT passwords** — `deploy/env/mqtt.env` ->
  `scripts/make-mosquitto-passwords.sh` -> `mosquitto/passwordfile`
  (gitignored, bcrypt hashes via `mosquitto_passwd` inside the official
  image if not installed locally).
- **Executor webhook token** — `EXECUTOR_WEBHOOK_TOKEN` shared between
  `gateway.env` and the lab-executor container env.
- For real deployments swap env files for your secret manager / docker
  secrets; the services only read env vars.

## MQTT ACL model

`deploy/mosquitto/aclfile` enforces per-device isolation at the broker:
each device may `write` only `sentinel/v1/<device_id>/telemetry` and `read`
only `sentinel/v1/<device_id>/command`. The `sentinel-gateway` account reads
all telemetry and writes all command topics. Anonymous access is disabled.

### Rover telemetry

`robotics/rover` publishes mission-state events over MQTT when configured:

```bash
MQTT_HOST=127.0.0.1 MQTT_PORT=1883 \
MQTT_TOPIC=sentinel/v1/rover-01/telemetry \
MQTT_USERNAME=device-rover-01 MQTT_PASSWORD=<from mqtt.env> \
MQTT_CLIENT_ID=rover-01
```

The topic MUST match the ACL (`sentinel/v1/<device_id>/telemetry`) and the
username MUST be that device's broker account. The gateway normalizes the
rover event shape into the canonical observation envelope
(`kind=mission_status`, gateway-assigned monotonic seq, deterministic
`event_id` from mission/command/event identity) before `ingestObservation`,
so replay protection and dedupe still apply.

### Mission downlink — WORKING via mission-shim

The module's `commandJson` is unsigned; the rover requires an
HMAC-SHA256 `signature` (PR #11) over its own contract. The bridge is
`services/mission-shim`: it subscribes each device's command topic with
that device's broker credentials, maps module types to rover types
(`patrol`→`patrol_route` via route map, `hold`→`stop`, …), signs with the
shared `ROVER_MISSION_SECRET`, and drops `<inbox>/<device>/<mission>.json`.
The rover consumes it via:

```bash
ROVER_MISSION_SECRET=<shared> PYTHONPATH=src \
  python3 -m rover_mission watch-missions <inbox>/rover-01
```

(`run-mission FILE` still works for single files.) See
`services/mission-shim/README.md` for env config and the type map.
Verified end-to-end: shim-signed `inspect_zone` mission → rover
navigated to `wp-rack-a` → evidence captured → `completed`.

### Executor service — real verification path

`apps/containment/executor` now ships an HTTP bridge
(`python -m containment_executor.service`, env `EXECUTOR_PORT`,
`EXECUTOR_TOKEN`, `EXECUTOR_ACTION_TTL_S`): POST `/execute` accepts the
gateway's outbox `payloadJson`, runs the approval-bound executor with
independent verification, and returns 200 only on `VERIFIED` (502
otherwise → gateway records `failed`). POST `/revert` drives the #35
recovery path. Point `EXECUTOR_WEBHOOK_URL` at it instead of the
record-only `deploy/lab-executor` stub for verified containment; the
stub remains the zero-dependency compose default.

## Tests / evidence

- `spacetimedb`: `cd spacetimedb && npm run test:smoke` — 44-check live
  contract test (authz, scoped views, correlation, action pipeline).
  **Requires a FRESH/EMPTY database** — the suite bootstraps its own
  genesis (`bootstrapAdmin` fails on an initialized directory). Run it
  before `deploy/seeds`, or against a scratch database that can coexist
  with the seeded lab:

  ```sh
  spacetime publish sentinel-hive-smoke --server http://127.0.0.1:3000 \
    --module-path spacetimedb --delete-data=always --yes
  cd spacetimedb && SPACETIMEDB_DATABASE=sentinel-hive-smoke npm run test:smoke
  ```

  (`SPACETIMEDB_URI`/`SPACETIMEDB_DATABASE` env overrides; identity-token
  cache is per-database.)

- `services/gateway`: `npx tsx test/gateway.test.ts` — 17-check MQTT
  ingest/mission/outbox integration test (in-process aedes broker +
  spawned gateway). Needs the stack up, module published, lab seeded, and
  `GATEWAY_TEST_TOKENS` — a JSON map of the `gateway`, `executor`,
  `commander`, `responder` tokens from `deploy/secrets/identities.json`:

  ```sh
  cd services/gateway
  GATEWAY_TEST_TOKENS="$(node -e 'const t=require("../deploy/secrets/identities.json")["ws://127.0.0.1:3000"];console.log(JSON.stringify({gateway:t.gateway,executor:t.executor,commander:t.commander,responder:t.responder}))')" \
    npx tsx test/gateway.test.ts
  ```

  Covers signed-envelope ingest (HMAC), duplicate/forged/stale rejection,
  mission downlink over MQTT, and the outbox worker. Re-runnable against a
  persistent database (seq base + incident titles are made unique per run).

- This deploy: `docker compose -f deploy/docker-compose.yml ps` shows all
  services healthy; `curl localhost:8081/healthz` after gateway start.

## Restart durability

- SpacetimeDB data lives in the named volume `spacetime-data` —
  `docker compose restart spacetimedb` (or `down`/`up`) preserves
  observations, devices, incidents, actions and views state. Verified:
  observations + `devices.lastSeq` survive a container restart.
- The ONLY wipe is `spacetime publish --delete-data=always` (bootstrap
  step 2) or `docker compose down -v`.
- Gateway restart reconciliation lives in `GATEWAY_STATE_FILE`
  (`services/gateway/gateway-state.json`, gitignored): dispatched-mission
  markers, completed outbox ids, and per-device seq counters for
  gateway-normalized telemetry survive gateway restarts.

## What is NOT here (by design)

- No dashboard hosting inside the lab network (docs/01/06) — clients are
  browser apps connecting to SpacetimeDB over the management plane.
- No committed secrets, no `.env` files, no real device credentials.
- No production/maincloud publish — `bootstrap.sh` targets `--server
  http://127.0.0.1:3000` (the compose instance); maincloud is a separate,
  explicit step.
