# Physical integration on the demo Mac

This is a lab setup, not a production deployment. On 2026-11-08 the team used a separate `blindspot-physical-*` database alongside the existing `sentinel-hive` database, without deleting or republishing its data. The selected database name is stored in gitignored `deploy/env/physical.env`. The dedicated MQTT container is `blindspot-physical-mqtt`. Broker, gateway and per-device credentials are stored under the owner-only gitignored `deploy/secrets/` and `deploy/env/physical-gateway.env`; never share or commit their contents.

## What was verified

- `pi-01` / `blindspot-pi1` (rack-01) and `pi-02` / `blindspot-pi2` (rack-02) run the original health and observation services plus the separate `blindspot-publisher` systemd user service.
- Each Pi signs its actual local measurements with a distinct HMAC key and publishes through a unique MQTT account over TLS. Gateway validation and matching SpacetimeDB rows were verified. The publishers persist sequence numbers before publishing and run under the `david` user; user lingering was enabled so their user services can survive logout.
- The approved pi-02 listener test detected TCP port 18082, created an incident, and cleared the alert after the listener stopped. The incident remained `New`, because the lifecycle does not allow an automatic transition from `New` to `Recovery`; an operator must triage it. Evidence without credentials is in gitignored `deploy/evidence/physical-node-acceptance.json` and `physical-listener-test.json`.
- The rover's camera streams through a loopback-only SSH tunnel into Rover Operations. Its MS200 LiDAR produced real scans during a stationary read-only test. The operator confirmed AprilTag 36h11 IDs 1 and 2 for rack-01 and rack-02; detection of those physical tags has not yet been verified. There is **no verified physical mission dispatch or live LiDAR map/pose feed**. The dashboard's motion and E-stop controls do not control the real rover.
- The gateway forwards physical observations to the local API, and the API schedules the scripted investigation orchestrator. A mission bridge process is connected; physical mission dispatch and end-to-end investigation have not been verified.

## Start and inspect

1. Connect all devices to the same authorized demo network. The broker certificate is tied to the laptop IP used at setup (`10.192.59.21`) and expires seven days after creation; if the IP changes or certificate expires, reprovision the broker certificate and the Pi trust files rather than bypassing TLS verification.
2. Start Docker and the existing `sh-spacetimedb` container. Do not run `deploy/scripts/bootstrap.sh` on the working setup: it uses destructive database publishing.
3. In a terminal on the Mac, run `deploy/scripts/start-physical-gateway.sh`. It starts the dedicated broker if needed and runs the gateway using the protected local config. `curl http://127.0.0.1:8081/healthz` should report MQTT and SpacetimeDB connected.
4. Establish the rover camera tunnel and run `deploy/scripts/start-physical-dashboard.py` in another terminal. The camera tunnel command is documented in [the dashboard README](../apps/dashboard/twin/README.md). Open `http://127.0.0.1:5188/`, select LIVE for physical Pi telemetry and Rover Operations for the camera. The dashboard server is bound to loopback and the development token is exposed to that browser; do not expose this server to a network.
5. On either Pi, `systemctl --user status blindspot-publisher` checks its publisher. Its TLS settings and unique credentials live in `~/.config/blindspot-publisher/publisher.env` (mode 600); its sequence lives in `~/.local/state/blindspot-publisher/sequence`. Never reset the sequence below the database's `lastSeq`.

## Boundaries and reset

The API process used so far is a local in-memory facade in scripted (`fake`) model mode. No live Nemotron inference, physical rover mission, physical tag recognition, physical SLAM registration, or containment has been demonstrated. The PiCar-X uses Ackermann steering; do not substitute the repository's older differential-drive/ESP32 motion paths for its existing motor-control code. The operator reported the physical E-stop and obstacle stop were tested; the integrated mission service still needs a verified independent stop path, a single motor/LiDAR owner, calibrated steering, supervised target search, and mission expiry handling before physical autonomy is enabled. The HTTP adapter can poll an asynchronous mission and requests abort when polling fails, but that is not a substitute for a rover-side watchdog or a deployed mission service.

For the controlled listener test, obtain operator approval first. The listener is `blindspot-listener.service` on pi-02; stop it with `sudo systemctl stop blindspot-listener` and confirm port 18082 is closed. Alert clearance does not automatically close the incident. Stop the gateway and dashboard with Ctrl-C in the terminals that started them. Stop the dedicated broker with `docker stop blindspot-physical-mqtt`; this does not stop the pre-existing MQTT container. Pi publisher services can be stopped with `systemctl --user stop blindspot-publisher` on each Pi. No ordinary reset requires deleting database data or credentials.
